### Two version facts that change how we build

**Tailwind is v4, so there is no `tailwind.config.ts`.** v4 is CSS-first: tokens are declared in
`globals.css` via `@theme`, not in a JS config object. All Phase 1 token work happens in CSS.
§3 flagged this as something to verify rather than assume — verified.

**Next 16 auto-generates `AGENTS.md`**, which states its APIs differ from model training data and
that `node_modules/next/dist/docs/` is the authoritative reference. That file is regenerated by
`next dev`, so it is committed rather than fought. Treat it as binding: read the shipped docs before
using an App Router API from memory. This is §3's "version-matched documentation" requirement, enforced
by the framework itself.

## 2. Design direction — "Andesite"

### 2.1 The grounding idea

*Pintu* means door. The **gapura** — the split gate that parts to let someone through — is the
structural motif. Structure, never clip art. No illustrated gate on the landing page.

### 2.2 The §4 stress test

> Would you have produced the same palette and type pairing for a fintech dashboard, a travel startup,
> and a study-notes app? If yes, it isn't a choice.

**Honest answer: the colour alone would.** Teal + gold + a red accent on warm off-white is a defensible
palette for any of those three. Hue is doing semantic work here (§2.4) but it is not doing *identity* work.

**So identity is carried by geometry instead** — three devices none of those three products would adopt:

| Device | What it is | Where it appears |
|---|---|---|
| **The seam** | A recessed 1px gutter — a hairline of `--ink` at low alpha with a 1px light catch on its far side — at every structural split. The gap in the gate, abstracted. | Rail↔content edge, the two Gapura panels, the Threshold's centre detent, the 8/4 split on detail pages |
| **Stepped arch** | Card top radius is 2× the bottom radius. Portrait cards run in an arch aspect. Terraced like a *candi bentar* silhouette, not a uniform rounded rect. | Every card, sheet header, the Gapura panels |
| **Paired asymmetry** | Structural splits are deliberately unequal — 8/4, 240/rest. Two gate halves, not a symmetric column set. | Detail pages, side rail, PathwayMap's major→destination split |

**What changed from the brief's starting proposal:** the brief offered a palette and asked for refinement.
The palette's *information logic* is kept exactly (§2.4). What was added is the geometric layer, because
the palette alone failed the stress test. Two token values were also corrected for accessibility (§2.5) —
those are fixes, not preferences.

### 2.3 Type

| Role | Face | Use |
|---|---|---|
| Display | **Bricolage Grotesque** (variable, `opsz` + `wdth` axes) | Large sizes only, with restraint |
| Body | **Geist** | Everything else |
| Numeric | **Geist Mono**, `tabular-nums` | Money, rates, hours, batch years |

Mono numerals do real work: this product is partly about earning, and tabular figures make amounts read
as data rather than marketing.

Fluid scale via `clamp()`, ~1.2 ratio at 360px widening to ~1.25 at desktop, exposed as tokens.
**No raw `font-size` in any component.**

All three load through `next/font`, which downloads at **build** time and self-hosts the output.
Verified after a production build: **14 `.woff2` files emitted, zero `fonts.googleapis.com` or
`fonts.gstatic.com` references anywhere in the client bundle.** Vendoring the files was the fallback
plan and is not needed.

### 2.4 Colour — six semantic tokens

**Hue carries meaning.** Red-family = income now. Teal-family = career later. Gold = verified.
No fourth accent. No gradients. A user should read the feed's temperature without reading a word.

| Token | Value | Job |
|---|---|---|
| `--ink` | `#14161C` | Text; dark-mode ground |
| `--merah` | `#CE1126` | Gigs, earning, primary action |
| `--laut` | `#0E7C7B` | Mentorship, growth, long horizon |
| `--emas` | `#C9A227` | Verification and trust **only** |
| `--kertas` | `#FAF7F2` | Light-mode surface (warm stone) |
| `--abu` | `#6E7583` | Secondary text, borders, disabled |

### 2.5 Contrast — measured, not assumed

Computed with the WCAG 2.1 relative-luminance formula. AA = 4.5:1 normal text, 3:1 large text.

**Light theme — text on `--kertas`:**

| Token | Ratio | Normal | Large |
|---|---|---|---|
| `--ink` | 16.92:1 | PASS | PASS |
| `--merah` | 5.26:1 | PASS | PASS |
| `--laut` | 4.69:1 | PASS | PASS |
| `--emas` | **2.26:1** | **FAIL** | **FAIL** |
| `--abu` | **4.33:1** | **FAIL** | PASS |

**Dark theme — text on `--ink`:**

| Token | Ratio | Normal | Large |
|---|---|---|---|
| `--kertas` | 16.92:1 | PASS | PASS |
| `--emas` | 7.48:1 | PASS | PASS |
| `--abu` | **3.91:1** | **FAIL** | PASS |
| `--laut` | **3.61:1** | **FAIL** | PASS |
| `--merah` | **3.21:1** | **FAIL** | PASS |

**The finding that matters.** The brief says dark mode is where this palette is strongest. As *fills*
that is true. As *text*, the opposite holds: **three of four accents fail AA for body text on dark ground.**
Shipping the six raw tokens straight into both themes would have shipped five accessibility failures.

**Resolution — accents are fills first, text second.**

Every accent-on-surface pairing we actually want is a **fill**, and every one of them passes:

| Fill pairing | Ratio | Use |
|---|---|---|
| `--ink` on `--emas` | 7.48:1 | VerificationBadge |
| `--kertas` on `--merah` | 5.26:1 | Primary action |
| `--kertas` on `--laut` | 4.69:1 | Mentorship action |
| `--kertas` on `--ink` / `--ink` on `--kertas` | 16.92:1 | Body text |

This also settles §4.2's "gold: verification and trust only — never decoration" as a *mechanical* rule
rather than a stylistic one: **gold is never text on light** (2.26:1 is unfixable without turning it olive).
It is a fill carrying `--ink`. In dark mode gold is the one accent that *does* work as text, at 7.48:1.

Where an accent genuinely must be text — an inline link, a stat — it uses a theme-specific variant.
Nearest-accessible starting values, derived by walking lightness until AA is met:

| Variant | Value | Ratio |
|---|---|---|
| `--abu-text` (light) | `#6B7280` | 4.52:1 |
| `--abu-text` (dark) | `#79808E` | 4.56:1 |
| `--merah-text` (dark) | `#F03348` | 4.54:1 |
| `--laut-text` (dark) | `#1F8D8C` | 4.52:1 |

`--abu` `#6E7583` is retained unchanged as `--abu-line` for borders and disabled states, where AA text
rules do not apply.

> These four were derived mechanically and shift hue slightly. Phase 1 hand-tunes them to preserve hue
> while holding the ratio, then re-measures. The ratios above are the floor, not the target.

The contrast script lives at `docs/reference/` — see §6 — and is re-run whenever a token changes.

### 2.6 Layout system

12 columns, 1200px max content width, 24px gutters desktop / 16px mobile. 4px spacing base as tokens;
**no arbitrary pixel values in components.** Two radii (card, control), expressed through the stepped-arch
profile. Three-step elevation ramp, preferring borders and background shifts over shadow stacks.

### 2.7 Motion budget

**One orchestrated moment, restraint everywhere else.** Scattered animation is the strongest tell that a
UI was generated rather than designed.

- **The moment:** Gapura reveal on first load. Two panels part, content settles in a short stagger.
  ~700ms, once per session, skippable, replaced entirely by a fade under `prefers-reduced-motion`.
- **Everywhere else:** 120–180ms hover/press, layout-animated reorder for the Threshold, route transitions.
- **Never:** loops, ambient float, parallax.

### 2.8 The Threshold (spec — built Phase 4)

One persistent rail between two poles: *Cuan sekarang* ←→ *Karier nanti*.

It **re-weights** the home feed in place; it does not filter. Cards reorder with layout animation, section
headers change, and page accent temperature slides along the `--merah` → `--laut` axis. Nothing is ever
removed from view — that distinction is the whole argument, and it is why this is not a filter chip.

Requirements: ARIA slider semantics with a live text description, arrow keys + Home/End, value persisted,
cross-fade fallback under reduced motion.

`rankByHorizon(items, threshold)` in `src/lib/ranking/threshold.ts` is a deterministic placeholder reading
`horizonScore` off each item. The real ranking model is `TODO(logic)`.

## 4. Rejected, and why

- **The three §4 defaults.** Cream + high-contrast serif + terracotta; near-black + single acid-green;
  broadsheet hairlines + zero radius. All are current defaults rather than decisions.
- **v0's five-tab IA** (Home / Explore / Applications / Mentorship / Profile). Separate Explore and
  Mentorship tabs are exactly the two-tab model §4.5 argues forfeits the 25% creativity category. Gigs and
  mentorship become two ends of one axis instead.
- **v0's `#e9424f` on `#f7f8fa`.** Generic SaaS red on cool grey. It carries no information: v0 used the
  same red for job cards and mentor cards, so hue told the user nothing.
- **Colour-led identity.** Considered and rejected in §2.2 — it failed the stress test.
- **Gold as a text colour on light surfaces.** 2.26:1. Not a preference; it cannot be made to work without
  becoming olive.

## 5. Carried forward from v0

The prototype (`docs/reference/prototype-v0.html`) had real instincts worth keeping:

- **Card anatomy** — logo chip → title → org → meta row → compensation → tags. Clean hierarchy, survives.
- **The match-reason line as a first-class card element.** v0 surfaced "why this matches you" on the card
  rather than burying it. This directly serves §2.3's "why not LinkedIn?" answer.
- **Chip filters** above the list, with an "All" default.

Not carried: its IA, palette, fonts, or any of its data.

## 6. Phase 0 notes and deviations

1. **shadcn/ui init deferred to Phase 1.** `shadcn init` writes its own CSS variable theme into
   `globals.css` — that is design-system work, and running it now would collide with the Andesite tokens
   before they exist. Radix primitives get installed per-component as they are actually used (§3:
   "install only components you use"). Flagging because §13 lists dependency install under Phase 0.
2. **`recharts` not installed.** §3 marks it "only if needed"; the PathwayMap is a hand-rolled
   deterministic SVG. Revisit only if a later surface needs a real chart.
3. **`@faker-js/faker` is a devDependency, deliberately.** Faker is ~5MB; shipping it to the client would
   put `/home`'s Lighthouse performance score at risk (§12 requires ≥90). Phase 3 generates the mock world
   at **build** time from the seed and serves it as static data, so faker never enters the client bundle.
   Keeping it in `devDependencies` makes accidental client-bundling a build error rather than a silent
   regression. Determinism is unaffected — same seed, same world.
4. **Scaffolded via a temp directory.** `create-next-app` rejects the `Pintu-Karir` folder name because npm
   package names cannot contain capitals. The app was scaffolded as `pintu-karir` and moved in; the package
   name is `pintu-karir`. No effect on the repo or the deployed app.
5. **Next telemetry disabled** — one fewer outbound request from the build, and it costs nothing.
6. **ESLint enforces §3's "no `any`, no `@ts-ignore`"** as errors rather than leaving it to discipline.
   Verified by deliberately introducing both violations and confirming the lint run failed on each.
   `tsconfig` adds `noUncheckedIndexedAccess` and `noImplicitOverride` on top of `strict`.
7. **The contrast checker** used to produce §2.5 is kept at
   `docs/reference/contrast-check.mjs`. Run `node docs/reference/contrast-check.mjs` after any token
   change. §4.2 requires contrast be "verified not assumed" — this is how it stays verified.

## 7. Open questions

Flagging now rather than guessing. None block Phase 1.

1. **`NEXT_PUBLIC_DEMO_MODE` vs "no environment variables required."** §11 gates DemoControls behind that
   variable; §14 requires a clean clone to run with zero configuration. **Proposal:** demo mode defaults
   **on** when `NODE_ENV === 'development'`, with the env var only needed to force it on in a production
   build. Clean clone works with no setup; deployed build stays clean unless asked.
2. **`/kitchen-sink` is "dev/demo builds only" (§5), but §15 requires every route to render with no 404s.**
   **Proposal:** the route always resolves. In a non-demo production build it renders a short "development
   surface" notice instead of the gallery. Never a 404, never a dead link.
3. **Should the Threshold drive Bricolage's `wdth` axis?** Tempting — the display face literally narrowing
   as the horizon lengthens. Risks layout shift and reflow cost on every slider tick. **Proposal:** decide
   from a rendered spike in Phase 1, not in the abstract. If it ships, it animates `font-variation-settings`
   on a fixed-width container so nothing reflows.
4. **Hue preservation on the four derived text variants** (§2.5). The mechanical derivation shifts hue
   slightly. Phase 1 hand-tunes and re-measures.
